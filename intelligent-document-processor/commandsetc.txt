What’s in it:

Ingestion: loaders for PDF, DOCX, HTML and Markdown, plus LLM extraction of a summary, key points, entities and topics.
Chunking: a recursive splitter with configurable size and overlap, and a semantic splitter.
Storage: text-embedding-3-large embeddings in Qdrant or Pinecone, with one collection per strategy.
API: a FastAPI service with /ingest, /ask and /documents.
Evaluation: evaluation/run_eval.py scores each strategy with RAGAS on faithfulness, context precision and context recall.
Dashboard: a Streamlit page comparing the strategies.
The 0.88 faithfulness / 0.84 context precision figures: I didn’t hard-code them. The eval script writes whatever scores your run produces, and the README says so. Run it on your own documents with 30+ question/reference pairs, since the bundled sample is only one document and five questions. how to run this

1. Set up
Unzip the project and open a terminal in it. You need Python 3.10+ and an OpenAI API key. Docker is only needed for Qdrant.

bash
cd intelligent-document-processor
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -e ".[dev]"
cp .env.example .env               # Windows: copy .env.example .env
Open .env and set OPENAI_API_KEY=sk-....

2. Start the vector database
Qdrant (default, local):

bash
docker compose up -d
Pinecone (alternative): in .env, set VECTOR_BACKEND=pinecone and PINECONE_API_KEY=.... Indexes are created automatically.

3. Run the API
bash
uvicorn idp.api:app --reload
Open http://localhost:8000/docs for an interactive page where you can try every endpoint.

Or use curl in a second terminal:

bash
# Upload and process a document
curl -F file=@data/sample_docs/remote_work_policy.md \
     -F strategy=recursive -F chunk_size=800 -F chunk_overlap=100 \
     http://localhost:8000/ingest

# Ask a question
curl -X POST http://localhost:8000/ask \
     -H "Content-Type: application/json" \
     -d '{"question":"How many remote days per week are allowed?","strategy":"recursive"}'

# See extracted summaries, key points and entities
curl http://localhost:8000/documents
Use strategy=semantic to try the other chunking method. Ingest and ask with the same strategy, because each strategy has its own collection.

4. Run the chunking comparison and dashboard
bash
python evaluation/run_eval.py --strategies recursive semantic
streamlit run dashboard/app.py
The first command ingests the docs in data/sample_docs/ under both strategies, answers the questions in evaluation/eval_questions.json, and scores them with RAGAS. It writes results/eval_results.json. The second opens the dashboard at http://localhost:8501.

To use your own data, put PDFs, DOCX, HTML or Markdown files in a folder and add your own question/reference pairs to eval_questions.json:

bash
python evaluation/run_eval.py --docs path/to/your/docs --questions path/to/questions.json
5. Run the tests (no API key needed)
bash
pytest

so what this does curl -F file=@data/sample_docs/remote_work_policy.md \
     -F strategy=recursive \
     -F chunk_size=800 -F chunk_overlap=100 \
     http://localhost:8000/ingest does it load it to the rag database

Yes. That command uploads the document to your API, and the API processes it and stores it in the vector database (Qdrant) so you can ask questions about it later.

What the command itself means
curl -F ... sends a file upload (a form POST) to your running FastAPI server.
file=@data/sample_docs/remote_work_policy.md is the file to upload. The @ tells curl to send the contents of that file.
strategy=recursive picks the chunking method.
chunk_size=800 and chunk_overlap=100 set the maximum chunk length in characters, and how many characters adjacent chunks share.
http://localhost:8000/ingest is the endpoint on your server that handles the upload.
What the server does with it
Load: it reads the file text (PDF, DOCX, HTML or Markdown).
Extract: it sends the text to the OpenAI chat model, which returns a title, summary, key points, entities and topics. These are saved to data/processed/<id>.json, and you can see them at /documents.
Chunk: it splits the text into pieces of about 800 characters, each overlapping the previous one by 100.
Embed: it sends each chunk to OpenAI text-embedding-3-large, which turns it into a vector (a list of 3072 numbers representing its meaning).
Store: it saves the vectors and the chunk text in the Qdrant collection idp-recursive. This is the “RAG database”.
The response you get back reports how many chunks were stored and how long it took.

How it connects to /ask
When you ask a question, the server embeds your question the same way and finds the chunks in idp-recursive whose vectors are closest to it. It sends those chunks and your question to the chat model, which writes the answer from them. That’s why /ask returned “I don’t know” with empty sources before: the collection was empty because nothing had been ingested yet.

You only need to ingest a document once. After that, you can ask as many questions as you like. To add more documents, run the same command with a different file, keeping the same strategy so they land in the same collection.

what this does run_eval.py --strategies recursive semantic

python evaluation/run_eval.py --strategies recursive semantic runs an automated experiment that answers one question: which chunking strategy gives better answers on my documents, recursive or semantic?

/ingest and /ask are for using the system. run_eval.py is for measuring it.

What it does, step by step
For each strategy you listed (recursive, then semantic), it:

Creates a fresh, isolated collection in Qdrant, named like idp-eval-recursive-<timestamp>. This keeps the experiment separate from your real data.
Ingests every document in data/sample_docs/ into that collection, using that strategy’s chunking. It skips the summary extraction, since that isn’t needed here.
Asks every question in evaluation/eval_questions.json. For each one it retrieves chunks, generates an answer, and records the question, retrieved chunks, answer and reference answer.
Scores the results with RAGAS, which uses an LLM as a judge:
Faithfulness: is the answer supported by the retrieved chunks, or did the model make things up?
Context precision: are the retrieved chunks relevant, and ranked near the top?
Context recall: did the retrieved chunks contain the information needed to match the reference answer?
Writes the averages to results/eval_results.json, along with the number of chunks and average chunk size per strategy.
Why both strategies?
They split text differently, so retrieval quality changes:

recursive cuts at fixed sizes (about 1000 characters) along paragraph and sentence boundaries.
semantic cuts where the meaning of the text shifts, so chunk sizes vary.
Running both on the same documents and questions gives a fair side-by-side comparison.

What you do with the output
The terminal prints one line per strategy with its scores. Then streamlit run dashboard/app.py reads the JSON file and shows them as charts and tables.

Things to know
It costs money and takes time. It makes many OpenAI calls (embeddings, answers, judging), and semantic chunking adds more embedding calls. The sample takes a minute or two and costs a few cents, but your own documents will cost more.
The sample is too small to be meaningful. One document and five questions will likely give near-identical, near-perfect scores. For real differences you need your own documents and 30+ question/reference pairs.
Each run leaves its eval collections in Qdrant. They’re harmless, but you can delete them from the Qdrant dashboard at http://localhost:6333/dashboard if you want to tidy up.
